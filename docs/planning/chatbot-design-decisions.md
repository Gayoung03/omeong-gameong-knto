# 챗봇 설계 결정

작성일: 2026-08-27 · 갱신: 2026-08-27 · 상태: **확정 28건 / 검색 도구 착수 가능**

[`docs/api/chatbot.md`](../api/chatbot.md)는 **엔드포인트와 통신 형식**을 정한 문서입니다.
이 문서는 그 위에서 **어떤 챗봇을 만들 것인가**를 정합니다.

## 요약

| 구분 | 내용 |
| --- | --- |
| 무엇 | 제주 반려동물 여행 **장소 추천 + 준비물 안내** 챗봇 (캐릭터: 혼디) |
| 검색 방식 | **도구 호출 기반 SQL 검색** — 임베딩·pgvector 쓰지 않음 |
| LLM 벤더 | **OpenAI** (저렴한 소형 모델로 시작) |
| 쓰기 동작 | **없음.** 장소 저장은 답변 속 카드의 버튼으로 사용자가 직접 |
| 응답 방식 | SSE 스트리밍 |

**진행 상황** — 대화 CRUD 6개 엔드포인트는 구현·테스트 완료했습니다.
검색 도구를 막고 있던 지역·카테고리·태그 어휘는 **DB 실제 값으로 확인**돼
[4장](#4-어휘--db-에서-확인한-실제-값)으로 옮겼습니다. 남은 것은 데이터 품질 안건과
[중지 버튼](#3-중지-버튼--명세-확정-조항을-다시-열어야-합니다)입니다.

## 0. 검색 방식을 도구 호출로 정한 이유

[`README.md`](../api/README.md)의 미정 항목 **"챗봇 RAG 검색 방식"**이 이걸로 해소됩니다.

GPT는 우리 `places` 테이블을 볼 수 없습니다. 그래서 답변 전에 우리가 먼저 장소를 찾아
재료로 건네줘야 하는데(= RAG), 그 **찾는 방법**으로 두 가지가 있었습니다.

| | 도구 호출 (채택) | 벡터 검색 |
| --- | --- | --- |
| 방법 | GPT가 `search_places(지역, 카테고리, 동반정책)`을 호출 → 우리가 SQL로 조회 | 장소 설명을 임베딩해두고 질문과 가까운 것 검색 |
| 강점 | 조건이 **정확히** 맞음 | 뉘앙스 질문("조용한 곳")에 강함 |
| 새로 만들 것 | 함수 하나 | 임베딩 배치, `vector` 컬럼 마이그레이션, 재색인 작업 |

**결정적인 이유** — 질문 `"강아지 실내 동반 되는 제주 동부 카페"`에서

- 도구 호출: `policy = 'indoor_allowed'`로 걸러 **실내 동반 되는 곳만** 나옵니다
- 벡터 검색: `"강아지 실내 동반 가능"`과 `"반려견 출입 불가"`는 문장이 거의 같아
  임베딩상 매우 가깝습니다. **동반 불가 카페가 섞여 나옵니다**

반려동물 앱에서 이건 검색 오류가 아니라 **챗봇이 "여기 데려가세요"라고 틀린 확신을 주는
사고**입니다. 사용자가 개를 데리고 갔다가 문 앞에서 돌아섭니다.

여기에 더해, 우리 데이터는 이미 `category`·`region`·`pet_policy_type`·`tags` 컬럼으로
나뉘어 있고, 필터 표현식은 [`app/services/place_query.py`](../../apps/api/app/services/place_query.py)에
전부 구현돼 있습니다.

> **pgvector는 나중에.** 리뷰 본문처럼 진짜 자연어 덩어리가 쌓이면 그때 얹습니다.
> `infra/docker-compose.yml`이 이미 `pgvector/pg16` 이미지라 문은 열려 있습니다.

## 1. 확정 사항

### A. 챗봇의 정체

| # | 항목 | 결정 |
| --- | --- | --- |
| A1 | 범위 | **장소 추천 + 준비물 안내.** 날씨는 제외(별도 API 있음) |
| A2 | 쓰기 동작 | **없음.** 챗봇은 저장하지 않고, 답변 속 장소 카드에 저장 버튼을 답니다 |
| A3 | 제주 밖 질문 | **정중히 거절** — "제주 여행만 도와드릴 수 있어요" |
| A4 | 무관한 잡담 | **짧게 받아주고 여행 이야기로 유도** |

**A2가 중요합니다.** 챗봇이 직접 저장하면 GPT가 의도를 오해해 엉뚱한 장소를 저장할 수
있는데, 버튼 방식이면 그 사고가 원천적으로 없습니다. **챗봇은 완전히 읽기 전용입니다.**

### B. 검색 도구

| # | 항목 | 결정 |
| --- | --- | --- |
| B3 | 도구 개수 | **2개** — `search_places`, `search_guides` |
| B4 | 도구 필터 | 지역·카테고리·동반정책·실내외·**태그·편의시설**·정렬·개수 |
| B5 | 반환 개수 | **5개** |
| B6 | 장소당 정보 | 이름·카테고리·지역·동반정책·평점 **+ 설명 80자** |
| B7 | 결과 0건 | **없다고 말하고 되묻기** — "애월에는 없네요. 근처 지역도 찾아볼까요?" |

**준비물은 새 테이블을 만들지 않습니다.** 다른 팀원이 **여행 가이드 테이블을 만드는 중**이라,
챗봇은 그 테이블을 읽는 `search_guides` 도구만 붙입니다. 콘텐츠가 두 벌이 되지 않습니다.

**B6에서 설명을 80자로 자르는 이유** — `description` 전문을 5개 넣으면 입력 토큰이
폭증합니다. 80자면 GPT가 "왜 이 곳을 추천하는지" 쓸 근거로는 충분합니다.

**B6에 `id`는 당연히 포함됩니다** — `referencedPlaces`에 실을 UUID입니다.

### C. 답변 생성

| # | 항목 | 결정 |
| --- | --- | --- |
| C1 | 모델 | **저렴한 소형 모델로 시작.** 품질이 부족하면 모델명만 바꿔 올립니다 |
| C2 | 대화 맥락 | **최근 10턴** |
| C3 | 답변 길이 | **3~4문장, 장소는 최대 3곳** |
| C4 | `referencedPlaces` | **GPT가 답변에서 실제 언급한 장소만** |
| C5 | 지도 표시 | **서버가 판단** — 장소가 있으면 지도, 없으면 글만 |
| C6 | `routeId` 대화 | **1차에서 제외.** `route_id`는 항상 `null` |

**C2에 상한이 필요한 이유** — 매 질문마다 지금까지의 대화를 통째로 다시 보냅니다.
상한이 없으면 ① 늦게 묻는 질문일수록 비싸지고 ② 언젠가 모델 입력 한도를 넘어
**챗봇이 에러만 뱉기 시작합니다.** 여행 대화는 보통 5~10턴이라 체감 차이는 거의 없습니다.

**C4 구현** — 검색된 5개 중 **답변 텍스트에 이름이 등장한 것만 거릅니다.**
GPT에 재질의할 필요 없이 문자열 매칭으로 끝납니다.

**C5** — 앱의 키워드 판단([`chatbotMapResponse.ts`](../../apps/mobile/src/features/chatbot/utils/chatbotMapResponse.ts))은
삭제합니다. 장소를 못 찾았는데 "카페"라는 단어만 보고 빈 지도가 뜨는 일이 없어집니다.

**C6** — DB 컬럼과 API 필드는 그대로 둡니다. 나중에 켤 수 있습니다.

### D. 대화 관리

| # | 항목 | 결정 |
| --- | --- | --- |
| D1 | 제목 자동 생성 | **첫 질문 앞 30자 자르기.** LLM 호출 0회 |
| D2 | 대화 개수 상한 | **100개, 넘으면 생성 거부** ("안 쓰는 대화를 지워주세요") |
| D3 | 보관 기간 | **지우지 않음.** 사용자가 직접 지울 때만 |
| D4 | `lastMessagePreview` | **20자** |

**D2를 자동 삭제로 안 한 이유** — 사용자가 저장해 둔 대화를 예고 없이 지우게 됩니다.
100개까지 채우는 사람은 챗봇을 아주 많이 쓰는 사용자인데, 하필 그 사람 것을 지웁니다.
번거로움과 데이터 유실 중에서는 번거로움이 낫습니다.

### E. 실패·한계·비용

| # | 항목 | 결정 |
| --- | --- | --- |
| E1 | 에러 문구 | **서버가 보낸 `detail`을 앱이 그대로 표시** |
| E2 | 타임아웃 | **첫 조각 20초 / 전체 60초** |
| E3 | 사용량 제한 | **하루 15회.** `ENVIRONMENT=local`이면 무제한 |
| E4 | 재시도 | **서버 자동 재시도 없음.** 앱의 재시도 버튼만 |
| E5 | 부적절한 질문 | OpenAI 필터 + **시스템 프롬프트에 규칙도 명시** |

**E1이 [`README.md`](../api/README.md)의 미정 항목 "에러 메시지 언어"를 해소합니다.**
[`chatbot.md`](../api/chatbot.md)의 에러 이벤트가 이미 `code`와 `detail`을 **둘 다** 내려주므로
**명세는 바꾸지 않습니다.** 앱이 `detail`을 쓰기로 한 것뿐이고, 나중에 특정 에러만
앱에서 꾸미고 싶어지면 그때 `code`로 분기하면 됩니다.

문구를 고치려고 앱스토어 심사를 기다리지 않아도 되는 게 이 선택의 이유입니다.

**E3** — [`config.py`](../../apps/api/app/core/config.py)에 `environment` 설정이 이미 있어
개발·테스트는 제한 없이, 운영만 하루 15회로 갑니다.

### F. 앱 화면

| # | 항목 | 결정 |
| --- | --- | --- |
| F1 | 대화 목록 화면 | **만든다.** 대화 목록 + 대화 상세, 화면 2개 추가 |
| F2 | 재진입 시 | **항상 새 대화.** 지난 대화는 목록에서 찾아 들어갑니다 |
| F3 | 스트리밍 중 | 깜빡이는 커서 + 입력창 잠금 + **중지 버튼** |
| F4 | 추천 질문 칩 | **"주변 동물병원이 어디에 있어?" → "제주시에 반려동물 병원 알려줘"** |

**F1로 엔드포인트 7개가 전부 살아납니다.** 명세를 축소할 필요가 없어졌습니다.

**F4가 필요한 이유** — 개인위치정보를 수집하지 않기로 확정했으므로 "주변"을 알 수 없습니다.
칩 하나가 **답할 수 없는 질문**을 사용자에게 권하고 있었습니다.

## 2. 결정에서 파생된 규칙

### 대화는 탭을 열 때가 아니라 첫 질문을 보낼 때 만듭니다

F2("항상 새 대화")와 D2("100개 상한")가 그냥 두면 부딪힙니다.
탭을 열 때마다 대화를 만들면 **질문도 안 한 빈 대화가 쌓여 100개가 금방 찹니다.**

→ 챗봇 탭은 빈 화면 + 추천 질문 칩으로 시작하고, **첫 질문을 보내는 순간 대화가 생성**됩니다.
[`chatbot.md`](../api/chatbot.md)의 `POST /chat/conversations`가 `firstMessage`를 함께 받게
돼 있어 **명세 변경 없이 됩니다.**

## 3. 중지 버튼 — 명세 확정 조항을 다시 열어야 합니다

F3에서 중지 버튼을 넣기로 했고, **중지하면 그때까지의 답변을 저장**하기로 했습니다.
[`chatbot.md`](../api/chatbot.md)의 2026-08-18 확정 조항 **두 개와 충돌**합니다.

| 현재 명세 | 필요한 변경 |
| --- | --- |
| "중간에 끊기면 저장하지 않습니다" | 사용자가 중지한 경우는 **예외로 저장** |
| "답변 생성 중지 버튼은 이번 범위에 없습니다" | 범위에 **포함** |

### 그런데 서버는 둘을 구분할 수 없습니다

사용자가 "그만"을 눌러도, 지하철에서 신호가 끊겨도,
서버 입장에서는 **똑같이 "클라이언트가 연결을 끊었다"**입니다.

```
사용자가 중지 버튼 누름   →  연결 끊김  →  저장해야 함
지하철에서 신호 끊김      →  연결 끊김  →  저장하면 안 됨
                             ↑ 서버는 이 둘이 같아 보입니다
```

**팀이 중지 버튼을 미룬 이유가 정확히 이겁니다** — 명세에도 "중단 신호를 보낼 방법과
'여기까지는 저장' 규칙이 함께 필요해서"라고 적혀 있습니다.

### 풀 수 있는 방법 (미결 — 팀 논의 필요)

| 방법 | 내용 | 걸리는 점 |
| --- | --- | --- |
| ⓐ 앱이 저장을 요청 | 중지 시 앱이 받은 텍스트를 서버로 보내 저장 요청 | 엔드포인트 1개 추가. 앱이 보낸 값을 믿어야 함 |
| ⓑ 중단 신호 엔드포인트 | `POST .../messages/stop`으로 "지금 중지" 신호 | 엔드포인트 1개 추가. 신호와 연결 끊김의 순서 경합 |
| ⓒ 끊기면 무조건 저장 | 구분을 포기하고 항상 저장 | 구현이 가장 쉽지만, 명세가 막으려던 "잘린 답변이 기록에 남는 문제"가 돌아옴 |

**이 결정은 이 문서에서 하지 않습니다.** 챗봇 명세 회의 안건입니다.

## 4. 어휘 — DB 에서 확인한 실제 값

> **2026-08-27 갱신 — 세 건 모두 DB 에서 실제 값을 확인했습니다.**
> 문서마다 표기가 달라 "정해야 할 것"으로 보였지만, **운영 데이터는 이미 한 벌로
> 돌아가고 있었습니다.** 회의에서 새로 정할 것은 아래 [남은 안건](#남은-안건)뿐입니다.

### B1. 지역 어휘 — 관광권역 6개

장소 1299건의 `region` 실제 분포입니다.

| 권역 | 장소 수 |
| --- | --- |
| 제주시/제주국제공항 | 677 |
| 애월/한림/협재 | 279 |
| 함덕/김녕/세화 | 159 |
| 표선/성산 | 111 |
| 서귀포시/모슬포 | 42 |
| 중문 | 27 |
| ~~제주시~~ · ~~서귀포시~~ | 3 · 1 — `seed_dev.py` 잔여물 |

**스키마 변경이 필요 없습니다.** `places.region` 은 이 권역 문자열을 그대로 두고,
GPT 에게 권역 목록과 방위 매핑을 시스템 프롬프트로 줍니다.

| 방위 | 권역 |
| --- | --- |
| 동부 | 함덕/김녕/세화, 표선/성산 |
| 서부 | 애월/한림/협재 |
| 남부 | 중문, 서귀포시/모슬포 |
| 제주시권 | 제주시/제주국제공항 |

### B2. 카테고리 어휘 — 12종, 다만 `etc` 가 21%

```
cafe 526 · etc 278 · attraction 149 · accommodation 148 · pet_service 82
restaurant 46 · beach 21 · restaurant_cafe 15 · oreum 12
veterinary_hospital 11 · walking_trail 8 · rental_experience 3
```

**`etc` 278건(21%)은 챗봇이 카테고리로 찾을 수 없습니다.** 다섯 곳 중 한 곳입니다.
`restaurant` 와 `restaurant_cafe` 도 겹칩니다. 둘 다 검색 품질을 직접 깎으므로
장소 데이터 회의 안건으로 넘깁니다.

앱 목업 `place.mock.ts` 는 여전히 한글(`카페·식당`)이라 **팀 규약("값은 영문 코드")
위반 상태**입니다.

### `place_tags` 목록 — 7종, 이미 영문 코드

```
sea · cafe · walk · photo_spot · experience · rest · indoor_tourism
```

`app/recommend/config/tags.py` 의 한글 `STANDARD_TAGS`(바다·카페·산책·포토스팟·
체험·휴식·실내관광)와 **1:1 로 맞아떨어집니다.** 추천 엔진은 한글 라벨을,
DB 는 영문 코드를 쓰고 있을 뿐 같은 7종입니다.

분위기 질문(“조용한 곳”, “사진 예쁜 데”)을 받아내는 것도 결국 이 태그입니다 —
`rest`, `photo_spot`, `sea` 로 번역하는 일은 GPT 가 합니다.

### 남은 안건

| 안건 | 왜 |
| --- | --- |
| `etc` 278건 분류 | 카테고리 검색에 안 걸림 |
| `restaurant` / `restaurant_cafe` 중복 정리 | 같은 것을 둘로 나눠 검색이 새어나감 |
| `제주시`·`서귀포시` 잔여 4건 정리 | 권역 목록에 없는 값 |

> **챗봇만의 문제가 아닙니다.** [`places.md`](../api/places.md) 의 장소 검색이 같은 값을
> 쓰므로 **장소 데이터 회의**에서 다룹니다.

## 5. 무엇을 먼저 만들 수 있나

```
[완료]       대화 CRUD 6개 엔드포인트  ─── LLM도 검색도 필요 없음
                    ↓
[다음]       search_places 도구        ─── 어휘 확인으로 막힘이 풀림
                    ↓
[디자인 대기] 앱 타입 정리 + 대화 목록·상세 화면 (F1)
                    ↓
[가이드 테이블 대기] search_guides 도구
                    ↓
[명세 회의 대기] 스트리밍 엔드포인트 + 중지 버튼
```

**앱 화면(F1)을 검색 도구보다 뒤에 둔 이유** — 디자인 시안이 없어 지금 만들면
시안이 나온 뒤 다시 만들 가능성이 큽니다. 검색 도구는 막힌 것이 없고,
만들다 보면 `etc` 278건이 실제로 얼마나 아픈지 수치로 나와 장소 데이터 회의의
근거가 됩니다.

## 6. 다음 결정이 필요한 것

| 안건 | 어디서 정할 것인가 |
| --- | --- |
| `etc` 278건 분류 · `restaurant`/`restaurant_cafe` 중복 · 잔여 4건 | 장소 데이터 회의 (`places.md`와 공동) |
| 중지 버튼의 중단 신호 방식 (ⓐ/ⓑ/ⓒ) | 챗봇 명세 회의 |
| 가이드 테이블 스키마 | 가이드 담당자 |
| 분위기 질문에 되물을지 / 못 한다고 말할지 | **검색 도구를 만들어 써본 뒤** |

### 분위기 질문은 지금 벡터로 바꿔도 해결되지 않습니다

"조용하고 분위기 좋은 카페" 같은 질문이 도구 호출 SQL 의 약점인 것은 맞습니다.
그런데 **지금 우리 데이터로는 벡터 검색도 똑같이 답하지 못합니다.**

| | 상태 |
| --- | --- |
| `description` 있는 장소 | 548 / 1299 (42%) |
| 평균 길이 | 52자 — 100자 넘는 것은 **2건** |
| 내용 | 분위기 서술이 아니라 `[KCISA] 강아지미용, 호텔 …` 분류 코드 덤프 |
| 리뷰 | **0건** |

벡터 검색은 글의 뜻을 찾는 기술이지 **없는 정보를 만들어내지는 못합니다.**
임베딩할 산문이 아직 없으므로, 지금 붙이면 파이프라인만 생기고 품질은 그대로입니다.

지금 받아낼 수 있는 만큼은 **태그 7종**입니다 — "조용한 곳"→`rest`,
"사진 예쁜 데"→`photo_spot`, "탁 트인 곳"→`sea`. 번역은 GPT 가 합니다.

**벡터를 붙일 시점은 리뷰가 쌓였을 때**입니다. 사용자 후기가 진짜 분위기
데이터이고, 그때 재설계 없이 얹을 수 있습니다.
