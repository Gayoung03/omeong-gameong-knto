# 챗봇 설계 결정

작성일: 2026-08-27 · 갱신: 2026-08-30 · 상태: **확정 31건 / 검색 도구 3개·SSE 스트리밍·중지 버튼 구현 완료 · 답변 품질 점검 진행 중**

[`docs/api/chatbot.md`](../api/chatbot.md)는 **엔드포인트와 통신 형식**을 정한 문서입니다.
이 문서는 그 위에서 **어떤 챗봇을 만들 것인가**를 정합니다.

| 무엇 | 제주 반려동물 여행 **장소 추천 + 준비물 안내** 챗봇 (캐릭터: 혼디) |

[모델 승격 여부](#6-다음-결정이-필요한-것)입니다.

## 0. 검색 방식을 도구 호출로 정한 이유

[`README.md`](../api/README.md)의 미정 항목 **"챗봇 RAG 검색 방식"**이 이걸로 해소됩니다.

GPT는 우리 `places` 테이블을 볼 수 없습니다. 그래서 답변 전에 우리가 먼저 장소를 찾아
재료로 건네줘야 하는데(= RAG), 그 **찾는 방법**으로 두 가지가 있었습니다.

| | 도구 호출 (채택) | 벡터 검색 |
| --- | --- | --- |
| 방법 | GPT가 `search_places(지역, 카테고리, 동반정책)`을 호출 → 우리가 SQL로 조회 | 장소 설명을 임베딩해두고 질문과 가까운 것 검색 |
| 강점 | 조건이 **정확히** 맞음 | 뉘앙스 질문("조용한 곳")에 강함 |
| 새로 만들 것 | 함수 하나 | 임베딩 배치, `vector` 컬럼 마이그레이션, 재색인 작업 |

**결정적인 이유** — 질문 `"강아지 실내 동반 되는 제주 동부 카페"`에서

- 도구 호출: `policy = 'indoor_allowed'`로 걸러 **실내 동반 되는 곳만** 나옵니다
- 벡터 검색: `"강아지 실내 동반 가능"`과 `"반려견 출입 불가"`는 문장이 거의 같아
  임베딩상 매우 가깝습니다. **동반 불가 카페가 섞여 나옵니다**

반려동물 앱에서 이건 검색 오류가 아니라 **챗봇이 "여기 데려가세요"라고 틀린 확신을 주는
사고**입니다. 사용자가 개를 데리고 갔다가 문 앞에서 돌아섭니다.

여기에 더해, 우리 데이터는 이미 `category`·`region`·`pet_policy_type`·`tags` 컬럼으로
나뉘어 있고, 필터 표현식은 [`app/services/place_query.py`](../../apps/api/app/services/place_query.py)에
전부 구현돼 있습니다.

> **pgvector는 나중에.** 리뷰 본문처럼 진짜 자연어 덩어리가 쌓이면 그때 얹습니다.
> `infra/docker-compose.yml`이 이미 `pgvector/pg16` 이미지라 문은 열려 있습니다.

## 1. 확정 사항

### A. 챗봇의 정체

| # | 항목 | 결정 |
| --- | --- | --- |
| A1 | 범위 | **장소 추천 + 준비물 안내.** 날씨는 제외(별도 API 있음) |
| A2 | 쓰기 동작 | **없음.** 챗봇은 저장하지 않고, 답변 속 장소 카드에 저장 버튼을 답니다 |
| A3 | 제주 밖 질문 | **정중히 거절** — "제주 여행만 도와드릴 수 있어요" |
| A4 | 무관한 잡담 | **짧게 받아주고 여행 이야기로 유도** |
| A5 | 건강·의료 질문 | **답하지 않는다.** 수의사에게 안내하고 동물병원 검색을 제안. 단 탑승·반입 **서류와 절차는 규정**이라 안내한다 |
| A6 | 이동수단 규정 | **도구로 찾아 안내하고 확인일을 밝힌다.** 판정은 도구가 계산한 값을 그대로 쓴다 |
| A7 | 미확인 정보 | **단정하지 않는다.** 도구 결과에 없으면 "확인되지 않았다"고 말한다 |
| A8 | 견종 제한 | **되는지 안 되는지 어느 쪽도 단정하지 않는다.** 특정 견종을 맹견·단두종으로 분류하지 않는다 |

**A2가 중요합니다.** 챗봇이 직접 저장하면 GPT가 의도를 오해해 엉뚱한 장소를 저장할 수
있는데, 버튼 방식이면 그 사고가 원천적으로 없습니다. **챗봇은 완전히 읽기 전용입니다.**

**A5 — 건강·의료는 범위 밖입니다.** "약 먹여도 되나요"만 막으면 부족합니다. 멀미·스트레스
대처처럼 **여행과 붙어 있는 건강 질문**이 실제로 더 많이 들어오고, 이쪽이 더 위험합니다.
거절만 하면 막힌 느낌을 주므로, 동물병원 검색은 실제로 되는 기능이니 그쪽으로 돌립니다.

**A6이 풀렸습니다(2026-08-28).** `search_transport_rules` 와 `search_guides` 를 붙여
`transport_pet_rules` 12건과 `guide_documents` 15편을 챗봇이 직접 읽습니다.
답변에는 `verified_at` 을 "2026년 8월 확인 기준"으로 붙이고, 규정이 바뀔 수 있으니
예약 전 확인을 권합니다.

**무게 판정은 파이썬이 합니다.** `12 > 7` 같은 비교를 GPT 에게 맡기지 않습니다 —
모델은 숫자 비교를 곧잘 틀리고, 여기서 틀리면 **공항에서 탑승을 거부당합니다.**
`guide_search._verdict()` 가 `가능 / 불가 / 무게 초과 / 가능하나 무게 기준 미확인 /
확인 안 됨` 다섯 중 하나를 내고, GPT 는 그 결론을 문장으로 옮기기만 합니다.

**`확인 안 됨` 을 `불가` 로 뭉개지 않습니다.** `TransportPetRule` 의 boolean 이 전부
nullable 인 이유와 같습니다 — 원문이 「불가」라고 밝힌 것과 우리가 확인하지 못한 것은
다릅니다. 뭉개면 없는 규정을 만들어 답하게 됩니다.

**A8 — 부분 목록이 목록 없음보다 위험합니다.** `transport_restricted_breeds` 테이블은
있지만 **데이터가 비어 있습니다.** 수집한 가이드 본문에는 견종이 예시로만 적혀 있고
("퍼그·시추·불독 **같은**", "도사견·핏불테리어 **등**"), `notes` 에는 "단두종은 위탁 불가"
라는 분류만 있어 견종 이름 자체가 없습니다.

예시만 채워 도구에 붙이면 **"우리 애 복서인데요?" 에 "가능합니다"라고 답합니다** —
복서도 단두종인데 목록에 없기 때문입니다. 목록이 아예 없으면 "확인하세요"라고 하는데,
부분 목록이 있으면 확신을 갖고 틀립니다. `is_example_only` 플래그를 모델에 만들어 둔
이유이기도 합니다. **전체 목록을 수집하기 전까지는 프롬프트로 막습니다.**

**한쪽만 막으면 반대쪽으로 샙니다(2026-08-28 실측).** 처음에는 "제한이 없다고 말하지
말라"만 넣었는데, 화면에서 `"우리 애 복서인데 위탁 돼?"` 를 물으니 **"복서는 허용되지
않는 맹견으로 분류됩니다"** 라고 답했습니다. 복서는 우리 데이터 어디에도 없고
동물보호법상 맹견 5종에도 없습니다. 결론이 보수적이라 덜 위험해 보이지만 **없는 규정을
만들어 답한 것은 같고**, 실제로는 탈 수 있는 아이를 못 탄다고 한 것입니다.
규칙을 **양방향**으로 고쳤습니다 — 특정 견종을 분류하는 것 자체를 막습니다.

**A7은 A6이 풀린 뒤에도 남습니다.** 규정 데이터에는 빈 칸이 있습니다(요금·소요시간 일부는
수집 때 미확인으로 남겼습니다). 빈 칸을 GPT 가 그럴듯하게 메우지 않도록 하는 규칙입니다.

### B. 검색 도구

| # | 항목 | 결정 |
| --- | --- | --- |
| B3 | 도구 개수 | **3개** — `search_places`, `search_guides`, `search_transport_rules` |
| B4 | 도구 필터 | 지역·카테고리·동반정책·실내외·**태그·편의시설**·정렬·개수 |
| B5 | 반환 개수 | **5개** |
| B6 | 장소당 정보 | 이름·카테고리·지역·동반정책·평점 **+ 설명 80자** |
| B7 | 결과 0건 | **없다고 말하고 되묻기** — "애월에는 없네요. 근처 지역도 찾아볼까요?" |

**준비물은 새 테이블을 만들지 않습니다.** 여행 가이드 테이블을 읽는 도구만 붙입니다.
콘텐츠가 두 벌이 되지 않습니다.

**B3을 2개에서 3개로 늘렸습니다(2026-08-28).** 가이드 데이터가 성격이 다른 두 벌이기
때문입니다 — `guide_documents` 는 사람이 **읽는 글**(준비물·입도 절차·렌터카)이고,
`transport_pet_rules` 는 **숫자로 거르는 값**(무게 상한·요금·신청 기한, 컬럼 22개)입니다.
`"12kg 인데 기내 되나요"` 는 숫자 비교라 글 검색으로는 답이 나오지 않습니다.
하나로 합치면 GPT 가 언제 무게를 넘겨야 하는지 헷갈려 합니다.

**B6에서 설명을 80자로 자르는 이유** — `description` 전문을 5개 넣으면 입력 토큰이
폭증합니다. 80자면 GPT가 "왜 이 곳을 추천하는지" 쓸 근거로는 충분합니다.

**B6에 `id`는 당연히 포함됩니다** — `referencedPlaces`에 실을 UUID입니다.

**겸업 카테고리는 서버에서 넓힙니다(2026-08-29, PR #154).** `restaurant` 를 물으면
`restaurant_cafe` 도, `cafe` 를 물으면 `restaurant_cafe` 도 함께 조회합니다.
`"반려동물 동반 되는 식당"` 에 후보가 **한 곳**뿐이었는데, 원인은 KCISA 원본이
`반려동물식당카페 > 카페` 하나여서 활성 기준 `restaurant` 1건 · `restaurant_cafe` 15건 ·
`cafe` 14건으로 갈린 것이었습니다.

**도구 스키마와 프롬프트는 그대로 두었습니다.** "식당을 물으면 겸업도 봐라"를 프롬프트에
적으면 모델이 매번 판단하게 되는데, 이건 판단할 것이 아니라 **항상 참인 매핑**입니다.
[C1](#c-답변-생성)에서 배운 것과 같은 갈래입니다 — 모델에게 맡길 수 있는 일과 맡기면 안
되는 일을 나눕니다. 화면 확인 결과 식당 질문이 1곳 → 3곳이 됐고, 챗봇이 "애견카페",
"식당 겸 카페"라고 **성격을 밝히면서** 답했습니다.

**데이터 쪽 재분류는 하지 않기로 제안했습니다**(장소 데이터 회의). 15건을 사람이 하나씩
가르려면 기준이 필요한데 원본에 그 기준이 없고, 정리해서 얻는 것이 "카테고리가
깔끔해진다" 뿐입니다.

### C. 답변 생성

| # | 항목 | 결정 |
| --- | --- | --- |
| C1 | 모델 | **저렴한 소형 모델로 시작.** 품질이 부족하면 모델명만 바꿔 올립니다 |
| C2 | 대화 맥락 | **최근 10턴** |
| C3 | 답변 길이 | **3~4문장, 장소는 검색 한 번당 최대 3곳** — 여러 권역을 검색했으면 합쳐서 여덟 문장까지 |
| C4 | `referencedPlaces` | **GPT가 답변에서 실제 언급한 장소만** |
| C5 | 지도 표시 | **서버가 판단** — 장소가 있으면 지도, 없으면 글만 |
| C6 | `routeId` 대화 | **1차에서 제외.** `route_id`는 항상 `null` |

**C1 — 소형 모델로는 부족한 사례가 나왔습니다(2026-08-28, 회의 안건).**

`gpt-4o-mini` 로 `"12kg 강아지 제주공항 기내 가능해?"`(회사를 안 집은 질문)를 물으면
**위탁을 세 번 연속 틀렸습니다.** 7곳 중 제주항공·티웨이·이스타는 위탁 제도가 없는데
`"모두 화물칸에 실을 수 있다"` 로 묶었습니다.

고치려고 세 가지를 순서대로 시도했습니다.

| 시도 | 방법 | 결과 |
| --- | --- | --- |
| 1 | 프롬프트에 "모두 ~하다로 묶지 말라" 추가 | 그대로 묶음 |
| 2 | 도구가 회사를 미리 분류해서 전달 | `위탁 제도 없음` 을 **`기내 탑승 불가`로 뒤집어** 적음 |
| 3 | 도구가 회사별 **결론 문장을 통째로** 전달 | 다시 `"위탁은 가능합니다"` 로 뭉갬 |

3번에서 모델이 받은 값은 `"기내 불가(상한 9kg 초과), 위탁 제도 없음 → 이 회사로는 이
무게로 갈 수 없음"` 입니다. **문장이 완성된 채로 들어갔는데도 반대로 썼습니다.**
`gpt-4o` 로 올리자 한 번에 정확해졌습니다 — 위탁 가능한 4곳만 정확히 골랐고, 시키지
않은 단두종 주의와 확인일까지 붙였습니다.

#### 6문항으로 넓혀 확인했습니다 (2026-08-29)

일화 한 건으로는 비용이 오르는 결정을 받을 수 없어, 8/28 오답 4건을 회귀 문항으로 넣고
여객선 다건 질문 2건을 더해 **같은 6문항을 두 모델로** 돌렸습니다(`make chat-check`).
전부 **회사·항로를 집지 않은 질문**입니다.

| | `gpt-4o-mini` | `gpt-4o` |
| --- | --- | --- |
| 실패 | **3.5 / 6** | **2 / 6** |

**다건 요약에서는 4o 가 확실히 낫습니다.** 12kg 질문에서 두 모델이 도구로부터
**완전히 같은 값**을 받았는데, 4o 는 위탁 가능한 4곳을 정확히 골랐고 mini 는
`"진에어, 대한항공, 아시아나항공 등"` 으로 3곳만 들고 흐렸습니다 — **"등"이
제주항공·티웨이·이스타도 되는 것처럼 읽혀**, 도구가 `"이 회사로는 갈 수 없음"` 이라고
완성해 건넨 사실이 지워집니다. 8/28 에 세 번 시도해 못 고친 지점이 여기서 고쳐집니다.

**다만 4o 로도 2건이 남고, 둘 다 모델 문제가 아닙니다.**

| 문항 | `gpt-4o` 가 한 것 | 실제 원인 |
| --- | --- | --- |
| `"항공사들 화물칸에 실을 수 있나요"` | **도구를 부르지 않고** 무게를 되물음 | **"무게를 몰라도 제도 유무는 먼저 찾아 답한다"가 프롬프트에 없다** (아래) |
| `"20kg 대형견 배로 갈 수 있나요"` | 도구의 `"무게 상한 미확인"` 을 **`"무게 제한 없이"`** 로 뒤집음 | 여객선에 무게 판정이 없다 — 아래 |

**2번의 원인은 되묻기 규칙이 있어서가 아니라 없어서입니다.** 프롬프트와 도구 설명
어디에도 "무게를 물어라"는 규칙이 없습니다 — 도구 설명은 `"무게를 알면 pet_weight_kg 에
넣는다"` 로 **허용**만 합니다. 그래서 무게를 모를 때 무엇을 할지는 모델이 고릅니다:
4o 는 되묻는 쪽을, mini 는 일단 찾는 쪽을 골랐습니다. `"화물칸에 실을 수 있나요"` 는
**제도 유무**를 묻는 질문이라 무게 없이 답할 수 있습니다. **"무게를 몰라도 제도 유무는
먼저 찾아 답한다"를 한 줄 넣으면 닫힙니다.**

**여객선에는 `_verdict` 가 나가지 않습니다.** `cabin_max_weight_kg` 가 5개 항로 전부
비어 있어 판정이 항상 `확인 안 됨` 이고, 실제 무게 조건은 `notes` 텍스트 안에만
있습니다(목포↔제주: 펫코노미 4kg · 펫스탠다드 10kg · 펫스위트룸 제한 없음).
**항공은 파이썬이 판정하는데 여객선은 모델이 `notes` 를 읽고 스스로 판단하고 있습니다** —
[2-3에서 세운 원칙](#c-답변-생성)이 여객선에서만 지켜지지 않았습니다. 20kg 은 공항이
아니라 **항구에서** 거절당하는 무게입니다.

목포는 **객실 등급마다 상한이 달라** 단일 컬럼으로 표현되지 않습니다. 컬럼을 늘리기보다
`notes` 의 무게 조건을 도구가 결론 문장에 얹는 쪽이 남은 기간에 맞습니다.

**8/28 오답 4건 중 ①③④ 는 4o 에서 재현되지 않았습니다.** A5(의료 경계)·A8(견종 단정
금지)은 두 모델 모두에서 유효했습니다.

**기본값은 아직 `gpt-4o-mini` 로 둡니다.** 비용이 오르는 결정이라 팀이 정해야 합니다
([6장](#6-다음-결정이-필요한-것)). 도구 호출로 여러 건을 돌려주는 질문에서 소형 모델이
요약하다 틀린다는 것이 이 안건의 근거입니다 — 데이터와 프롬프트 쪽으로 할 수 있는
것은 위 세 가지로 다 해봤습니다.

**C2에 상한이 필요한 이유** — 매 질문마다 지금까지의 대화를 통째로 다시 보냅니다.
상한이 없으면 ① 늦게 묻는 질문일수록 비싸지고 ② 언젠가 모델 입력 한도를 넘어
**챗봇이 에러만 뱉기 시작합니다.** 여행 대화는 보통 5~10턴이라 체감 차이는 거의 없습니다.

**C4 구현** — 검색된 5개 중 **답변 텍스트에 이름이 등장한 것만 거릅니다.**
GPT에 재질의할 필요 없이 문자열 매칭으로 끝납니다.

**C5** — 앱의 키워드 판단([`chatbotMapResponse.ts`](../../apps/mobile/src/features/chatbot/utils/chatbotMapResponse.ts))은
삭제합니다. 장소를 못 찾았는데 "카페"라는 단어만 보고 빈 지도가 뜨는 일이 없어집니다.

**C6** — DB 컬럼과 API 필드는 그대로 둡니다. 나중에 켤 수 있습니다.

**C3 의 "최대 3곳"이 개수 상한으로 읽히고 있었습니다(2026-08-29, PR #155).**
`"제주 전체에서 카페 추천해줘"` 처럼 권역을 여러 번 검색하는 질문에서, 모델이 찾아놓은
곳을 버리거나 반대로 3곳 규칙을 무시하고 늘어놨습니다.

**곳 수를 못 박지 않고 문장 수로 바꿨습니다** — 검색 한 번당 3곳, 여러 권역을 검색했으면
합쳐서 **여덟 문장**까지. 사용자가 실제로 불편해하는 것은 곳 수가 아니라 **답변이
길어지는 것**이고, 권역이 몇 개나 걸릴지는 질문마다 달라 미리 정할 수 없습니다.

**F3에서 입력창 잠금을 뺐습니다(2026-08-30).** 원래는 답변이 오는 동안 입력창을
아예 잠갔는데, 답변이 몇 초씩 걸리는 동안 **다음 질문을 미리 적어둘 수 없었습니다.**
지금은 입력은 되고 **전송만 막습니다** — 막는 이유("두 질문이 겹치면 어느 답변이
어느 질문의 것인지 알 수 없다")는 전송에만 해당하지 타이핑에는 해당하지 않습니다.
전송 버튼 자리는 답변 중에 **중지 버튼**이 됩니다.

#### 답변은 타이핑하듯 흘립니다 — 도착 속도와 표시 속도를 분리 (2026-08-30)

스트리밍을 붙이고 화면에서 눌러보니 **체감이 나빴습니다.** 두 번에 걸쳐 고쳤고,
**첫 시도는 틀렸습니다.** 그 기록을 함께 남깁니다.

| | 증상 | 한 것 | 결과 |
| --- | --- | --- | --- |
| 1차 | "너무 빨리 끝나서 굳이인 느낌" | 800ms 안에 끝나면 **통째로 표시** | ✗ **"너무 빡! 나온다"** |
| 2차 | 위 | **타이핑 속도로 흘리기** | ○ |

**1차가 왜 틀렸나** — 모아뒀다 한 번에 뿌리는 것이라, 문제였던 "왈칵"을 오히려 **더 크게**
만들었습니다. 임계값을 넘겨 흘리는 경우에도 모아둔 것을 통째로 얹어 같은 일이 났습니다.

**진짜 원인은 서버 조각을 그대로 그린 것**이었습니다. 조각은 일정한 속도로 오지 않습니다 —
모델이 토큰을 묶어 보내고 네트워크가 뭉치면 `"카페 두 곳을 "` 처럼 어절이 통째로 툭
들어옵니다. **도착 리듬이 그대로 화면 리듬이 되니** 울퉁불퉁했습니다.

그래서 **도착과 표시를 분리**했습니다. 조각은 `target` 에 쌓기만 하고, 화면은 제 속도로
그것을 따라갑니다(`useChatbot.ts`).

#### 타이핑 스펙 (2026-08-31 확정)

| 항목 | 값 |
| --- | --- |
| 진행 단위 | **글자 하나씩** |
| 글자당 간격 | **20~40ms** 랜덤 |
| `.` `,` `?` **뒤** | **100~200ms** 추가 |
| 커서 | 타이핑 위치에서 깜빡이는 **`\|`** (500ms 주기) |
| 건너뛰기 | **채팅 영역 아무 데나** 누르면 즉시 전체 표시 |

매번 랜덤을 뽑는 것은 기계적인 등간격을 피하려는 것이고, 문장부호 뒤에 쉬는 것은 읽는
호흡을 만들려는 것입니다.

```
onDelta  → target 에 쌓기만 (화면 갱신 없음)
타이머   → 한 글자 전진 후, 방금 찍은 글자를 보고 다음 딜레이를 정해 자신을 재예약
done     → 완성본을 들고만 있다가, 타이핑이 따라잡으면 그때 확정 메시지로 교체
```

글자마다 딜레이가 달라 **고정 간격 타이머(`setInterval`)로는 표현할 수 없습니다.**
재귀 `setTimeout` 입니다.

> **긴 답변은 느립니다 — 그래서 건너뛰기가 필수입니다.** 글자당 평균 30ms 라 300자
> (여덟 문장, [C3](#c-답변-생성))면 **9초 안팎**입니다. 실측 8.8초. 이걸 감수하기로 하고,
> 대신 **화면을 누르면 즉시 전부** 보이게 했습니다. 한 번 누르면 그 뒤에 도착하는 조각도
> 기다리지 않습니다 — 사용자가 "빨리"라고 밝힌 의사를 되돌리지 않습니다.

**`done` 을 받자마자 확정 메시지로 바꾸면 안 됩니다.** 화면이 아직 못 따라간 나머지가
통째로 튀어나와, 고치려던 "왈칵"이 **마지막에 그대로 재현**됩니다. 타이핑이 끝난 뒤에
교체합니다.

**표시 속도를 우리가 정하므로 1차의 불만("너무 빨리 끝난다")도 함께 풀립니다** — 짧은
답변도 최소한의 시간에 걸쳐 흘러갑니다. 서버·명세는 건드리지 않았습니다.

> **중지 버튼의 의미가 구간마다 다릅니다.** 받는 중이면 연결을 끊습니다(답변 저장 안 됨).
> `done` 뒤 **타이핑만 남은 구간에는 끊을 것이 없으므로**(답변은 이미 저장됐다) 타이핑을
> 건너뛰고 완성본을 바로 보여줍니다.

> **남은 것 — 도구 호출 구간의 침묵.** 실제 대기의 대부분은 장소를 찾는 구간인데 그동안
> 화면은 스피너뿐입니다. `stream_answer()` 가 도구 라운드에서 내보낼 텍스트가 없어서입니다.
> 여기를 채우려면 서버에 진행 이벤트를 추가해야 해서(명세·서버·앱이 모두 바뀝니다) 별도로
> 다룹니다. **"빨리 끝나서 굳이"의 나머지 절반이 여기 있습니다.**

**F4가 필요한 이유** — 개인위치정보를 수집하지 않기로 확정했으므로 "주변"을 알 수 없습니다.
칩 하나가 **답할 수 없는 질문**을 사용자에게 권하고 있었습니다.

## 3. 중지 버튼 — **결정됨(2026-08-30): 중지해도 저장하지 않습니다**

원래 F3에서 중지 버튼을 넣으면서 **중지하면 그때까지의 답변을 저장**하려 했고,
그것이 [`chatbot.md`](../api/chatbot.md)의 2026-08-18 확정 조항 두 개와 충돌했습니다.

### 막혔던 지점 — 서버는 둘을 구분할 수 없습니다

사용자가 "그만"을 눌러도, 지하철에서 신호가 끊겨도,
서버 입장에서는 **똑같이 "클라이언트가 연결을 끊었다"**입니다.

```
사용자가 중지 버튼 누름   →  연결 끊김  →  저장해야 함
지하철에서 신호 끊김      →  연결 끊김  →  저장하면 안 됨
                             ↑ 서버는 이 둘이 같아 보입니다
```

**팀이 중지 버튼을 미룬 이유가 정확히 이겁니다** — 명세에도 "중단 신호를 보낼 방법과
'여기까지는 저장' 규칙이 함께 필요해서"라고 적혀 있었습니다.

### 결정 — **저장 요구를 버렸습니다**

세 안(ⓐ 앱이 저장 요청 / ⓑ 중단 신호 엔드포인트 / ⓒ 끊기면 무조건 저장) 모두
"중지 시점까지 저장한다"를 전제로 두고 방법을 고르는 것이었습니다.
**그 전제를 버리면 문제 자체가 사라집니다.**

| | 결과 |
| --- | --- |
| 중지 버튼 | **범위에 포함.** 앱은 연결만 끊는다 |
| 중지 시 답변 | **저장하지 않는다** — 기존 "중간에 끊기면 저장 안 함"을 그대로 적용 |
| 새 엔드포인트 | **없음** |
| 서버가 둘을 구분 | **안 한다** (구분할 필요가 없어졌다) |

**왜 이쪽인가** — ⓑ는 "중지 신호"와 "연결 끊김"이 어느 쪽이 먼저 닿을지 모르는
순서 경합을 만들고, ⓐ는 앱이 보낸 텍스트를 서버가 **그대로 믿어야** 합니다(앱이 실제로
받은 내용인지 서버가 검증할 방법이 없습니다). ⓒ는 명세가 막으려던 "잘린 답변이 기록에
남는 문제"를 되돌립니다. 셋 다 얻는 것이 "중지한 답변도 남는다" 하나뿐인데,
**사용자가 중지를 누르는 이유는 보통 그 답변이 마음에 안 들어서**입니다.

사용자에게는 **"중지 = 답변 취소"** 로 읽히고, 질문은 `start` 시점에 저장돼 있어
다시 물어볼 수 있습니다.

> **다시 열릴 조건** — "중지한 답변도 기록에 남기고 싶다"는 요구가 실제로 생기면,
> 그때 위 ⓐ/ⓑ가 다시 안건이 됩니다. 지금은 그 요구가 없습니다.
